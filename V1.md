# Paravoid v1 implementation contract

Selected implementation design, 2026-09-21. **Not shipped functionality or a
frozen interoperable protocol.** This closes the product/design choices left open
in [PACKAGING.md](PACKAGING.md) and [DISTRIBUTION.md](DISTRIBUTION.md). Where those
documents leave a choice open, this document selects it. Existing experiment
formats remain experimental; do not silently label them v1.

Implementation discoveries may require explicit amendments here. A wire freeze
requires shared executable vectors, independent Python/Android verification and
security review. “Defined”, “implemented”, and “verified” are separate milestones.

## 1. Scope and finish line

V1 is an ordinary Android app packaged automatically into a fixed shell and a
complete, independently signed VPK, with transparent cold-start updates. It includes
public and APK-provisioned-key delivery, embedded and empty shells, recovery and
minimal shell-owned controls. No store app, store API, Activity annotation,
downstream resource module or manual bootstrap script is required.

- Preserve all supported app/library Activity, service, receiver and provider
  declarations. Changing their installed contract requires a shell APK update;
  changing their implementation does not. The one-Activity rule is not returning.
- V1 retains exactly one MAIN/LAUNCHER destination and rejects Activity aliases and
  additional launcher categories/destinations. Broader launcher routing is deferred,
  not a reason to reject ordinary non-launcher library Activities.
- Complete packaging requires shell minSdk 30. Normal builds keep their own
  minimum and normal APK/AAB behavior. Existing DEX-only mode remains explicitly
  selectable; it does not gain full-VPK delivery by implication.
- Same-UID named app processes are in scope. Isolated processes and direct-boot
  payload components are outside the initial complete-packaging profile and must
  produce actionable build errors, not silently broken artifacts.
- Initial automatic integration targets AGP 8.13.2. AGP 9 integration is a
  separately tested adapter gate for Pezzottify, not an inferred compatibility claim.
- Shell distribution v1 targets a standalone APK. Normal AABs remain supported;
  shell split-APK/AAB personalization and configuration-targeted VPKs are deferred.
- Release APK signing is required; R8/resource shrinking remain explicitly rejected
  until their own implementation gates pass. A signed, unshrunk release is valid v1.

These are initial support boundaries, not restrictions newly enforced by this
documentation change. Existing compatibility fixtures remain regression evidence
for their documented modes, including modes broader than this initial profile.

## 2. Build API and reproducible outputs

The extension is `paravoid`. The complete packaging configuration below is now
implemented; installed-device acceptance and the broader finish-line gates remain
separate from build-level validation.

Implementation progress: optional `baselineDirectory` and `pinnedResources` are
now available, with narrower resource-ledger and resource-boundary analysis/check
workflows described in README.md.
The explicit `package<Variant>ParavoidResourceShell` task now builds signed,
embedded-resource APKs with production early loading. This intermediate stage
does not implement `packaging = 'complete'`, the full-VPK format or updater.
Opt-in complete packaging now adds automatic signed shell assembly, complete-VPK
production, APK-pinned policy and complete baseline exports; see
[the implementation guide](paravoid-gradle-plugin/COMPLETE-VPK.md).

```groovy
paravoid {
    packaging = 'complete'              // or 'dexOnly'; migration default dexOnly
    bootstrap = 'embedded'              // or 'empty'
    payloadVersion = 42L                // positive, publisher-assigned, never reused
    baselineDirectory = layout.projectDirectory.dir('paravoid/baseline')
    pinnedResources = ['drawable/notification_icon']
    updates {
        enabled = true                 // default false for local packaging work
        baseUrl = 'https://updates.example.test/'
        channel = 'stable'
        authentication = 'public'      // or 'apkKey'
        trustPolicyFile = layout.projectDirectory.file('paravoid/trust.json')
    }
    signing {
        keyId = 'release-2026'
        privateKeyFile = providers.environmentVariable('PARAVOID_SIGNING_KEY')
            .map { file(it) }           // PKCS#8; never packaged or logged
    }
}
```

Keep applicationId/suffix configuration in the existing AGP flavor DSL. Default
shell suffix remains `.paravoid`; external callback registrations remain the app's
responsibility. Optional Hilt/Work compatibility stays in optional modules.

`empty` requires complete packaging and enabled updates. Enabled updates require
an HTTPS endpoint and an explicit public trust policy. Local embedded debug builds
may use an explicitly generated development signing key; release builds must fail
without configured signing. No production bypass for unsigned VPKs. Debug-only HTTP
requires an explicit opt-in and is forbidden in release outputs.
The base URL must end in `/`, with no userinfo, query or fragment; store its
normalized scheme/host/default-port form as the exact grant audience. A deployment
path prefix is supported and is part of the audience. Channel is fixed by the APK.

For each shell variant, expose `package<Variant>ParavoidVpk`,
`check<Variant>ParavoidContract`, and `export<Variant>ParavoidBaseline` tasks.
Normal assemble/bundle tasks are unchanged; shell assemble consumes the produced
VPK when embedded and never embeds it when empty. No implicit network publishing.

Outputs under `build/outputs/paravoid/<variant>/`:

- `payload.vpk`, `release.json` (the identical signed manifest from the archive),
  and `payload.sha256` (lowercase hex final-archive hash plus newline).
- `shell-contract.json`, `resource-ledger.json`, `packaging-report.json` and a
  readable `packaging-report.txt` explaining ownership, pinned roots/closure,
  rejected features, compatibility changes and trust key IDs, never credentials.
- `baseline-candidate/`: reviewable baseline, never an automatic modification of
  source-controlled files. The downstream developer explicitly promotes it into
  the configured baseline directory and commits it for a new shell generation.

No baseline means a new shell generation. An existing baseline is immutable build
input. Ledger IDs remain stable; removed resources retain tombstones. Parallel
release branches must reconcile the ledger before publication. Payload builds
against a baseline fail on shell-bound changes, with a concrete diff.
Baselines are variant-scoped: `<baselineDirectory>/<variant>/resource-ledger.json`
and, once implemented, that variant's shell contract and pinned-resource inventory.
Promote newly published ledger allocations as well as new-shell baselines; ordinary
builds never perform that promotion. These documents separate the fixed installed
baseline identity from the evolving reservation ledger.

The contract ID is SHA-256 of RFC 8785 canonical UTF-8 descriptor bytes. The
descriptor includes installed identities/declarations, SDK/process/capability
requirements, runtime ABI, pinned resource IDs/configurations/content, ledger
baseline, trust policy, endpoint/channel/auth mode and bootstrap mode. Exclude
payload bytes/version, private build paths, timestamps and per-install grants.
APK versionCode alone does not invalidate a contract. Adding unused movable
resource IDs extends the release ledger, not the installed baseline hash.
Endpoint, channel or trust-policy changes therefore require a new shell contract;
replacing only a per-install grant does not. V1 has no runtime channel switcher.

## 3. Complete package format

VPK format 1 is a single-disk ZIP with STORED outer entries, no encryption, ZIP64,
comments, extra fields, data descriptors, directory entries, symlinks, duplicate
names, overlapping extents or trailing/prefixed bytes. Local and central headers
must agree; CRC32 and signed SHA-256 are both checked. Writers use fixed timestamps
and sorted names. Paths are case-sensitive ASCII using only the names below.

| Path | Contents |
| --- | --- |
| `release.json` | Signed release envelope, not part of its own inventory |
| `code/classes.dex`, `code/classes2.dex`, … | Contiguous multidex sequence; no `classes1.dex` |
| `resources.apk` | Complete linked Android resource table/configurations and ordinary assets |
| `java-resources.jar` | Merged non-class Java resources, including service descriptors |
| `native/<abi>/<name>.so` | Per-ABI libraries, when present |
| `resource-ledger.json` | Full release ledger extending the installed baseline |

All paths except optional native entries and extra DEX files are required. The
JAR is present even if empty. Its merge/conflict semantics follow the app's AGP
packaging configuration; classes and DEX inside it are forbidden. Native names
contain only ASCII letters, digits, `_`, `-`, `+`, `.` and end in `.so`; ABI names are
`arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`. Unknown roles/paths are rejected.

Implementation amendment, 2026-09-22: `+` is allowed because the standard Android
C++ runtime is named `libc++_shared.so`; the earlier character restriction would
incorrectly reject ordinary NDK applications.

Use the shared `0x7f` namespace and generated stable R/styleable linking from
PACKAGING.md. The shell contains only runtime/bootstrap plus pinned content.
Identical pinned entries may also occur in resources.apk; changed pinned bytes
are incompatible. Do not leave movable content in the shell as a fallback.

Nested APK/JAR archives may use STORED/DEFLATE but must be inventoried and bounded
during validation: no encrypted entries, duplicate/unsafe paths, links or ZIP64.
Do not recursively extract arbitrary embedded assets; they are app-owned bytes.
Native libraries are extracted only to private immutable version directories;
resources and Java resources are loaded only from the selected generation.
Choose the first device-preferred ABI compatible with the app process bitness
and present in the signed release, never mix
libraries across ABIs, and reject when native code exists but no ABI matches.
Resolve dependencies from that generation plus Android's permitted platform
libraries, not an older payload or stale installed app libraries.

Hard v1 ceilings: 1 GiB VPK, 1 MiB release envelope, 4,096 outer entries, 100,000
combined APK/JAR entries, 2 GiB combined uncompressed component content, 128 MiB
per DEX, 256 MiB per native library, nesting depth 32 for JSON, 4 KiB per ordinary
string and 255 bytes per archive path. Encoded envelope bodies are exempt from the
ordinary-string bound but remain subject to envelope bounds. Reject before
allocation/extraction where possible. Streaming counters enforce actual bounds,
not merely attacker-supplied header sizes. Oversized apps need a future profile,
not silently relaxed runtime limits.

Implementation amendment, 2026-09-22: bound the resource-ledger JSON to 16 MiB and
100,000 reservations so parsing cannot allocate an archive-sized object graph.
Runtime ABI 1 initially accepts standard little-endian DEX 035/037/038/039 with
112-byte headers and matching SHA-1/Adler checksums; newer DEX containers require
an explicitly tested runtime-ABI extension. Nested APK/JAR containers use UTF-8
safe paths and contiguous local records, without APK signing blocks or hidden
prefix/gap/trailer bytes. The generated resource APK is unsigned. Ordinary ZIP
extras and data descriptors remain supported, except ZIP64/encryption/link records.
Nested local extra areas may end with one to three zero bytes emitted by Android
`zipalign` for four-byte alignment. Nonzero tails, truncated central extra fields,
and all outer-VPK extra fields remain rejected.

## 4. Shared signing and metadata profile

All signed objects use a JSON envelope with exactly three fields:
`keyId`, `body`, `signature`. The last two are padded standard Base64 without
whitespace. Body bytes are UTF-8 JSON; sign the exact bytes, never a reserialization.
Reject duplicate JSON keys, invalid Unicode, non-integral numbers, unknown fields
and missing required fields. No optional critical-extension mechanism in v1:
extensions require a protocol/format revision. Object field order is irrelevant
to parsing; writers use RFC 8785 canonical bytes for reproducibility.

The signature input is ASCII `paravoid/v1/<role>\n` followed by decoded body
bytes, where role is `release`, `head` or `grant`. Algorithm:
RSA-3072, exponent 65537, SHA-256 with RSASSA-PKCS1-v1_5, public key DER
SubjectPublicKeyInfo. No algorithm negotiation. SHA-256 values are lowercase
64-character hex. Integers are 0 through 2^53-1; version/revision values start at
1. Times are integer Unix seconds. Identifiers except applicationId match
`[A-Za-z0-9_-]{1,64}`. ApplicationId is the installed Android package name.

The APK-pinned trust policy contains `version: 1`, `applicationId`, and separate
`releaseKeys`, `headKeys`, `grantKeys` maps from keyId to Base64 DER public key.
It also contains `minimumPayloadVersion` and `minimumHeadRevision` floors for the
configured channel/contract. At least one release key and, with updates enabled,
one head key are required; apkKey also requires a grant key. The three key sets
must not share key material. A listed key authorizes only its own role for that
application and installed policy. Require exactly one trusted signature per object.

No online delegations, downloaded trust roots or online root revocation in v1.
Provision multiple trusted keys before a planned rotation; removing a compromised
key or adding a new root requires a shell APK update. Credentials and signing keys
are different things. This deliberately does not claim TUF-equivalent compromise
resilience; a compromised release authority can authorize malicious code. Keep
release private keys offline/in release infrastructure, separate from the server's
online head key. Threshold signing and online root rotation are future work.

Release body fields, all required:

| Field | Meaning |
| --- | --- |
| `version` | `1` |
| `applicationId`, `shellContractId` | Installed identity and exact contract SHA-256 |
| `releaseId`, `payloadVersion` | Immutable publisher ID and increasing app-lineage version |
| `runtimeAbi`, `formatVersion` | Positive runtime ABI integer; format `1` |
| `minSdk`, `maxSdk` | Inclusive bounds; maxSdk `0` means no upper bound |
| `abis` | Unique supported ABI strings; empty means no native-code restriction |
| `ledgerSha256` | Hash of exact resource-ledger bytes |
| `inventory` | Path-sorted array of `{path, size, sha256}` covering every other entry exactly |

Release signatures do not expire: already accepted apps must work offline. A
fresh signed head authorizes accepting a new downloaded release. Embedded VPKs
are authorized by the installed APK and release signature without a network head.
Publisher allocation of payloadVersion is global to the application lineage,
including different contracts/channels; rebuilding different bytes needs a new
version and releaseId. ReleaseId and version mappings are immutable once published.

## 5. Discovery, download and freshness

Use the DISTRIBUTION.md routes. GET head query parameters are exactly `contract`,
`channel`, `sdk` (integer), `abis` (ordered comma-separated device ABI list filtered
to the app process bitness),
`runtime` (integer), `format=1`, `protocol=1`; UTF-8 percent-encode values.
Reject duplicate parameters. The head signs this normalized request scope so a
cache cannot substitute another device/contract/channel response.

Head envelope maximum is 64 KiB. Required body fields: `version: 1`,
`applicationId`, `shellContractId`, `channel`, `sdk`, `abis` (ordered array),
`runtimeAbi`, `formatVersion: 1`, `headRevision`, `issuedAt`, `expiresAt`, `status`,
`release`. Status is `available`, `no-compatible-release` or
`shell-update-required`. `release` is null for the last two; for available it is
exactly `{releaseId, payloadVersion, manifestSha256, archiveSha256, archiveSize}`.
Manifest hash covers exact release.json envelope bytes. The immutable download
route is derived from applicationId/releaseId; v1 has no arbitrary download URLs,
CDN-origin delegation or signed-URL tickets. Signed release requirements are
checked again after download; discovery is not a substitute for validation.

Successful metadata responses use `application/json`; VPKs use
`application/vnd.paravoid.vpk`. Require HTTPS, normal platform certificate
validation, and `Accept-Encoding: identity`; reject content encoding other than
identity. All redirects are errors, including same-origin redirects. Reverse
proxying behind the configured origin is fine. No credential-bearing URLs/logs.

Heads use strong ETags equal to quoted SHA-256 of exact response bytes and
`Cache-Control: private, no-cache`; responses vary on Authorization. Clients keep
a private verified cache. 304 is valid only with the exact request/credential
scope and a still-fresh previously verified body; it never extends expiration.
The server authenticates before 200, 206 or 304. A 404 is an error, not authenticated
absence. 401/403 stop automatic attempts until explicit retry or APK credential
replacement; never retry anonymously. Existing verified payloads remain usable.

VPK responses use `Cache-Control: private, no-cache`, Content-Length equal to the
signed size and strong ETag equal to quoted archive SHA-256. Support a single
`Range: bytes=<offset>-` with `If-Range`. Validate 206 offsets/total/validator;
200 replaces the partial; 416 discards the partial and permits one full retry.
Never execute a partial; rehash the entire result and validate all components.
Grant/contract changes discard partials. Publishers make archives durable before
publishing a head and retain referenced versions throughout head validity.

Timeouts: connect 15 seconds, read-idle 30 seconds; downloads stream in bounded
chunks. Retry network failures, 429 and 5xx at most three times per attempt with
1/4/16-second jittered delays; honor Retry-After seconds up to one hour by scheduling,
not blocking startup. A persisted partial may resume on a later eligible attempt.

Head lifetime must be positive and at most 24 hours; allow issuedAt at most five
minutes ahead of device time, but never extend expiresAt. Require current time
strictly before expiresAt. Persist the highest authenticated time/revision and
payload-version knowledge transactionally. Reject clocks over five minutes behind
the authenticated time floor; show “check device time”, not a verification bypass.
Within a boot also use elapsed time so clock rollback cannot extend cached validity.

Revision high-water scope is app/contract/channel, not signing key, grant or device
capabilities. Equal revisions may describe different request scopes; for an equal
revision and identical scope require identical signed body bytes. Servers increment
the revision whenever any response in that scope changes, including expiry.
Payload-version high-water is app-lineage-wide. A lower newly offered version is
rejected; an equal version must have the same previously known release identity
and hashes. No automatic channel-switch downgrade. Existing accepted offline
execution does not depend on a new head or unexpired credentials.

First installation/data clear restores only APK-pinned floors: there is no trusted
network time or persistent history surviving uninstall promised here. A plausible
but wrong clock can reject good updates or admit otherwise expired discovery on a
fresh install. Document this limit; local root/data tampering is outside the threat
model. Exclude grants, caches, high-water state and payload directories from Android
backup. Corrupt anti-replay state fails closed for new downloads and requires a
shell repair update with explicit floors, or an explicit user data reset; never
quietly reset counters.

## 6. APK-provisioned authentication

Public mode sends no Authorization header. apkKey mode sends
`Authorization: Bearer <key>` on every head/download/range request. Key is 32 random
bytes encoded unpadded Base64url (43 characters); grants carry an opaque keyId for
support/auditing separately from the signing envelope's issuer keyId. No user ID is
required on the wire. Server-side user association is the distributor's concern.

Select APK signing-block personalization, not store re-signing, as the v1 carrier.
Reserve private candidate entry ID `0x50564132` for the signed grant envelope;
maximum 16 KiB and exactly one entry. It is distinct from the fixture ID and must
be checked for ecosystem collision before wire freeze; it is not a registered ID.
Grant body fields: `version: 1`, `applicationId`, `shellContractId`, `audience`,
`grantId`, `keyId`, `key`, `issuedAt`, `expiresAt`. Audience is the exact configured
base URL; expiresAt `0` means distributor revocation only. Otherwise it must exceed
issuedAt. Apply the same future-issued clock tolerance as heads.

Issuer trust comes only from APK-pinned grantKeys. Grants cannot replace trust,
endpoints or installed policy. Missing, duplicate, malformed, expired, wrong-scope
or invalidly signed records deny updates. There is no asset fallback that would
mask stripping or malformed records, no login and no client-side refresh endpoint.

The personalization tool writes a new output APK, preserves and verifies developer
v2/v3 signatures, then verifies the inserted record. Refuse malformed APKs and
unsupported signing layouts. Regenerate whole-file checksums and any v4 idsig as
applicable; do not reuse them. Installer/store transport must preserve this record;
stripping it results in denied update access, not public fallback.

Read the installed base APK at each process startup; cache only in memory for its
installed-file identity. Credential changes invalidate HTTP caches/partials and
auth-error suppression, but not accepted payloads or anti-replay counters. Revoking
a key blocks future server access. Replacement is a newly authorized APK install
with a newly issued grant; test package replacement while old processes/requests
exist. No promise that changing a grant can cancel an already authorized transfer.
Same key may be copied with the APK; this is entitlement transport, not DRM.

## 7. Startup, selection and multi-process coordination

One generation consists of validated code/resources/Java resources/native files
plus immutable signed metadata. No component-level selection and no hot swap.
Install resource/native paths before loading user Application classes, custom
factories or providers; preserve normal provider/Application.onCreate order.
Framework and app-created configuration contexts must see the same generation.

Persist a checksummed, versioned atomic selection journal in private no-backup
storage: selected generation, pending candidate, last healthy generation, trial
state, rejected generations and signed-identity references. Fsync content before
publishing selection and fsync directory metadata as required. Never trust journal
labels instead of signatures/hashes. Version directories are immutable after
verification and not overwritten in place. Verify before each process loads them.

Use OS-backed interprocess locks, not PID lists/timeouts as proof of process death:
a short exclusive selection lock plus a shared generation lease held for the whole
payload process lifetime. Selection/cleanup require an exclusive lease, acquired
non-blockingly under the selection lock. Every starting process takes the selection
lock, decides the generation and acquires its lifetime lease before releasing that
lock. Use one consistent lock order. If existing payload processes hold leases,
new processes join their generation and the pending update waits. Lock semantics,
process death and startup races must be proven on-device before shipping.

A shell-only recovery/bootstrap process never loads user code and takes no payload
lease. It can fetch/verify/stage even when the selected payload is corrupt. If all
payload processes exit, the next cold start may select a pending candidate. Do not
kill unrelated processes or silently restart an app in active use to force updates.
An always-running app service can consequently delay activation indefinitely;
surface “ready; waiting for app processes to stop”.

Before entering user code, durably mark a new candidate trial. Main-process trial
health requires successful Application.onCreate and the first resumed Activity's
first rendered frame. Background-only startup remains trial, not proven healthy.
A completed startup records progress even if no Activity is launched. Process kill
or power loss before progress is not proof of a bug: permit two incomplete cold
generation attempts, then pause automatic payload entry in recovery. Count a new
attempt only when no prior-generation process lease remains, not once per joining
worker. Successful background startup clears the incomplete-attempt count without
marking the UI healthy. A caught startup failure
quarantines immediately. Other processes may join the selected trial generation;
their caught startup failures quarantine it too. Never switch generation underneath
processes already running it. Health is a startup signal, not proof of app/data
correctness; later crashes are not automatic rollback triggers.

## 8. Empty shells, recovery and persistent data

Embedded is default and works offline from first launch. Empty omits only the VPK,
not bootstrap UI, pinned resources, installed declarations or trust policy. It can
fetch the current compatible release; no requirement to preserve a historic first
VPK forever. Empty mode is explicitly opt-in because background entry before the
first successful bootstrap cannot behave like an installed full app.

With no runnable payload (empty, corrupt or quarantined), component construction
uses shell-owned unavailable implementations through the installed factory:

| Entry | Required absent-payload behavior |
| --- | --- |
| Launcher or another Activity | Show bootstrap/recovery; never construct the missing class |
| Started service | Stop promptly, non-sticky; satisfy foreground-service timing when applicable |
| Bound service | Return no binder; callers must handle unavailable binding |
| JobService | Finish with reschedule requested; never claim the work completed |
| BroadcastReceiver | Return promptly without work/success claims or network blocking |
| ContentProvider | Preserve authority/permission enforcement; operations fail explicitly as unavailable, not empty successful results |

Do not replay broadcasts, binder transactions, provider operations, jobs or
arbitrary Activity intents after download. Bootstrap shows a retry action for
external callers; after activation only a fresh ordinary launcher Intent is
generated. Deep links/auth callbacks may therefore need retry while no payload
exists. User URI grants/sensitive extras are not persisted for later replay.
Non-replayable background events may be lost during initial bootstrap/recovery;
apps requiring those events before first launch should use embedded shells.

Unavailable JobService/foreground/bound-service/provider implementations must be
generated/tested against the declared component kind; a generic plain Service
is not a valid universal stand-in. Do not suppress security checks or fabricate
app-specific protocol responses. Any manifest component kind with no valid
unavailable adapter blocks empty-mode packaging until one is implemented.
Embedded-mode corruption must still fail closed with a clear recovery route.

Never automatically execute an older payload after a candidate entered user code:
Application/providers may already have migrated persistent data. Retaining an old
archive is not retaining an old database. V1 recovery is forward-only: publish a
new higher-version repair VPK (possibly restoring old code with data-compatible
fixes), retry an intact quarantined version only with explicit user confirmation,
or install a repair shell APK. No generic rollback button, automatic data deletion,
database snapshot scheme or “safe to downgrade” inference.

Pre-execution rejection leaves the selected generation untouched. Corrupt payload
bytes do not prevent authenticated repair: bootstrap reads trust/grants from the
APK, preserves anti-replay floors, and stages a verified compatible replacement.
An identical known release may be re-downloaded for byte repair; different content
under an existing release/version is forbidden. A shell contract change makes old
payloads incompatible; use the new embedded payload or empty bootstrap without
erasing app data. The new APK must not silently bypass payload-version floors.

## 9. Controls, scheduling and storage

Provide shell-owned bootstrap/recovery/update screens, reachable without loading
payload code. Required actions: check now, retry, cancel download, view current and
pending identities/errors/storage, toggle automatic checks/downloads and restrict
automatic downloads to unmetered networks. Default: automatic checks/downloads
enabled on any network; normal usable-app foreground entry checks at most once
per six hours, asynchronously. Empty bootstrap checks immediately. Explicit check
ignores the interval but not authentication/security rules. No required background
scheduler/store service in v1 and no blocking network in application startup.

Activation occurs only at the coordinated cold boundary, even after a manual
check. UI explains how to close/relaunch if a version is waiting. Recovery UI must
not expose credentials or offer “ignore signature”/“clear app data” shortcuts.

Default retention: active, one most recent previous healthy generation, and at
most one pending candidate. Failed candidates keep bounded diagnostic metadata,
not unlimited archive copies. Users may retain zero through three previous
generations for diagnostics/future repair, not arbitrary execution rollback.
Cleanup never removes a leased generation, active selection or pending trial.
Before downloading or extracting an embedded archive, acquire the runtime's single
cross-process update-space admission and require `3 * archiveSize + 64 MiB` free:
incoming archive, private verification copy and materialized outer STORED inventory.
The verifier bounds that inventory by archive size; nested APK/JAR contents are not
recursively extracted. Direct staging of an existing source requires two copies
plus the same headroom. Downloads derive size from authenticated admission metadata.
This is serialized admission, **not physical disk preallocation**: unrelated writers
can still exhaust storage, so preparation rechecks actual capacity and IO may fail.
The claim covers transfer through staging, holds no selection lock, fails busy with
`UNAVAILABLE`, and releases on close or process death. Embedded temporary input is
removed before release or reaped by the next owner after interruption.
Lifecycle cleanup removes only unprotected, unleased history and abandoned staging;
configured retained history, active/pending generations and security records survive.
Delivery cleans only its own partials. Insufficient capacity leaves the active app
usable; a failed update never resets authenticated version knowledge.

## 10. Implementation sequence and definition of done

Implement and commit small verified slices in this order; use the current fixtures
as regression controls, not replacements for product acceptance:

1. Baseline/ledger/contract reports and AGP integration; automatic shared-namespace
   resource linking/pinning with ordinary app/library generated R/styleables.
2. Full archive assembly and early resource/assets/Java-resource/native loading;
   embedded A/B builds against a fixed shell and no installed movable fallback.
3. Exact wire schemas and checked-in positive/negative binary/JSON vectors; Python
   reference producer/server and production Android verifier agree on every bound,
   signature, capability, cache and rejection rule above. Security review and
   signing-block ID collision review precede wire freeze.
4. Production discovery/auth/download/staging plus APK personalization CLI. Keep
   reference server store-agnostic; do not add a store catalog/upload model here.
5. Atomic selection, leases, whole-app startup/trials and authenticated repair;
   fault-inject process death, power-loss boundaries, corruption and storage errors.
6. Empty-shell component adapters and shell-owned controls; exercise every entry
   type both before bootstrap and during recovery, with no store app installed.
7. Fixed-shell real-app full VPK A-to-B updates, offline restart, revoked/replaced
   grants, incompatible shell rejection and forward repair. Pezzottify remains the
   target; its AGP adapter and actual critical workflows must pass, not just build.

Every relevant gate runs normal packaging as a control and shell on API 30 and
36.1; release readiness additionally requires a physical ARM64 device and signed
release outputs. Cover multiple app processes, Hilt/Work, providers, library
Activities/auth callbacks, Room migrations, reflection/service resources, native
dependencies, configuration changes, alarms/jobs/binder and app data preservation.
Re-run existing compatibility tests when touching their boundary. Record exact
platform/toolchain versions, timings, sizes and failures in the compatibility matrix.

V1 is done only when these gates pass and the public docs describe implemented
behavior with reproducible evidence. This document alone does not satisfy a gate.
Deferred: targeted/delta distribution, dynamic installed-component changes, hot
swap, generic data rollback, online trust delegation, extra launcher routing,
isolated/direct-boot payload execution, shell AAB delivery and unproven shrinking.

## Design references

- [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) defines the canonical JSON
  encoding used for reproducible descriptors/writers; signatures verify exact bytes.
- [TUF specification](https://theupdateframework.github.io/specification/latest/)
  informs the rollback, freeze, mix-and-match and key-compromise threat review.
  Paravoid's fixed APK trust profile is not TUF and does not implement its threshold
  roles or online root-update protocol.
- [Android AppComponentFactory](https://developer.android.com/reference/android/app/AppComponentFactory)
  is the public construction boundary for app components. The availability adapters
  and early-resource ordering above still require implementation/device proof.
